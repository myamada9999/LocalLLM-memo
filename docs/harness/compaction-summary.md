# 引き継ぎメモの中身 — 5つのハーネスは要約に何を書かせるか

[AIの「机の片付け」](compaction.md)の続きです。
前の記事では、片付け（コンパクション）の違いを3つの質問で見ました。このページでは、3つ目の「メモは誰がどう書く？」を掘り下げます。

- AIを使わない処理は、具体的に何をしているのか
- AIが書く引き継ぎメモには、どんな見出しがあるのか
- その違いに、どんな良い点と弱い点があるのか

1〜3章は、各ハーネスのソースコードにある指示文と処理を読んで確かめた内容です（2026年11月時点。確かめた版は6章）。
4章の「良い点と弱い点」は設計を読んだうえでの考察で、実際に要約させて比べた結果ではありません。

言葉は前の記事と同じです。

| このページでの言い方 | 意味 |
|---|---|
| 机 | AIが一度に見られる量 |
| 片付け | コンパクション |
| 引き継ぎメモ | 古い会話の要約 |
| 作業結果 | コマンドの出力や、読んだファイルの中身 |

---

## 1. 先に結論

- **AIを使わない処理は、要約ではありません。** 中身を読まずに、決まった規則で「切る」「外す」「記録から一覧を作る」処理です。5つのハーネスすべてにあります。
- **AIが書くメモの見出しは、DSH が8つ、Cline Desktop が5つ、Pi が6つ、OpenCode が7つです。** Codex は見出しを決めていません。
- **見出しのある4つに共通するのは「目的」「進み具合」「次にやること」です。** 差が出るのは、エラーの経緯、ファイル、制約の扱いです。
- **見出しの数だけでは優劣は決まりません。** 見出しが少ないハーネスは、依頼の原文をそのまま残す、ファイルの一覧を記録から足す、といった別のしくみで補っています。

---

## 2. AIを使わない処理は、何をしているか

### 3種類に分けられる

| 種類 | やること | 例 |
|---|---|---|
| 切る | 長いものの一部だけを残す | DSH の中抜き、Pi の2,000文字切り |
| 外す | 古いものを机の上から下ろす | Codex の古い記録、Cline Desktop の古い作業 |
| 記録から一覧を作る | 「どのファイルを読んだか」などを作業の記録から拾う | Cline Desktop の注記、Pi のファイル一覧 |

どれも、文章を読んで大事かどうかを判断してはいません。

- **良い点**: 速く、AIの利用料がかからず、作り話が混ざりません。
- **弱い点**: 大事な1行が切られる場所にあっても、残りません。

もとの記録は残ります。変わるのは、机の上（AIに見せる部分）だけです。

### ハーネスごとの処理

| ハーネス | AIを使わない処理 | AIの要約との関係 |
|---|---|---|
| **DSH** | 8,192文字を超える作業結果を、先頭4,096文字と末尾1,024文字だけにする（中抜き） | 要約の前の下ごしらえ。これで足りれば、AIは呼ばない |
| **Codex**（自分で書く場合） | ユーザーの発言を、新しい順に約2万トークン分そのまま残す。要約の依頼が机に入りきらないときは、いちばん古い記録を1件ずつ外してやり直す | 要約と組み合わせる |
| **Cline Desktop** | ① 依頼は全部残し、古い作業を一覧の注記に置き換える。② メモの「Files」の欄を、作業の記録から埋める | ① は要約の代わり（要約が失敗したときと、机があふれた直後）。② は要約の補強 |
| **Pi** | AIに見せる作業結果を、1件2,000文字に切る。読んだファイルと変更したファイルの一覧を、メモの末尾に足す | 要約の前と後 |
| **OpenCode** | 要約の依頼が大きすぎるとき、会話をテキストに直して、古いやり取りから4段階で縮める | 要約の前（入りきらないときだけ） |

Codex には、メモ作りを提供元のサーバーに任せる方法もあります。その場合の中身は外から確認できないので、このページでは「自分で書く場合」だけを扱います。

### 実際の形

**DSH: 中抜き**

長い作業結果は、次の形に置き換わります。3万文字のテスト結果なら、約5,200文字になります。

```
（先頭の 4,096 文字）

[... tool result middle pruned ...]

（末尾の 1,024 文字）
```

対象は作業結果だけで、会話の文章には手をつけません。片付けを始める位置を超えたときに、長いものをまとめて中抜きします。

**Codex: ユーザーの発言を残し、古い記録を外す**

- ユーザーの発言を新しいものから順に取り、合計が約2万トークンになるまでそのまま残します。
- 入りきらなくなった1件は、途中で切って残し、そこで止めます。
- 画像などが付いた発言は、文字の部分だけにします。
- 残した発言の後ろに、AIが書いた要約を置きます。

**Cline Desktop: 古い作業を一覧に置き換える**

落とした作業の代わりに、次の注記が入ります。直近3件までの回答文も、この中にそのまま残ります。

```
<SYSTEM_NOTICE>
Earlier context was compacted. Summary of your actions after the request above:
Files read:
（読んだファイル）

Files edited:
（編集したファイル）

Commands ran:
（実行したコマンド）

Your recent responses:
（直近の回答文）
</SYSTEM_NOTICE>
```

残し方の規則は、[前の記事の4章](compaction.md#aiを使わない短縮は具体的に何をしているか)にあります。

**Pi: 作業結果を先頭だけにし、ファイルの一覧を足す**

AIに要約を頼むとき、作業結果は先頭の2,000文字だけを見せます。

```
（作業結果の先頭 2,000 文字）

[... 28000 more characters truncated]
```

できあがったメモの末尾には、記録から作った一覧を足します。

```
<read-files>
（読んだだけのファイル）
</read-files>

<modified-files>
（変更したファイル）
</modified-files>
```

**OpenCode: 4段階で縮める**

要約の依頼が大きすぎるときは、会話を「[User]: …」「[Assistant]: …」というテキストに直し、次の順で縮めます。

| 段階 | 縮め方 |
|---|---|
| 1 | 作業結果を2,000文字に切る（先頭と末尾を1,000文字ずつ残す） |
| 2 | 作業結果を外す。道具に渡した内容は2,000文字に切る |
| 3 | ユーザーの発言だけを残す（長ければ2,000文字に切る） |
| 4 | そのやり取りを丸ごと外す |

- 古いやり取りから順に1段階ずつ縮めます。全部を縮めても入らないときだけ、次の段階に進みます。
- 最新のやり取りは、丸ごと外すことはしません。
- 提供元に「長すぎる」と断られるたびに、目標を小さくします（最初に断られた大きさの85%、70%、50%、35%）。
- 画像などは「[種類 omitted]」という印に置き換えます。

## 3. AIが書くメモの見出し

### ハーネスごとの見出し

**DSH（8つ）**

| 見出し | 書く内容 |
|---|---|
| Primary Request and Intent | ユーザーの依頼と意図。最初の目的と、途中で変わった目的。言い回しが大事なところは原文で引用 |
| Key Technical Concepts | 使っている技術、枠組み、決まりごと |
| Files and Code | ファイルの正確な場所と、なぜ大事か。主な変更やコードの一部 |
| Errors and Fixes | エラーと、その直し方。関係するユーザーの指摘 |
| Pending Jobs | はっきり頼まれていて、まだ終わっていない作業 |
| Current Work | この時点でやっていた作業 |
| Next Step | 次の一手を1つだけ（直近の依頼に沿うもの） |
| Critical Context | 決めたことと理由、制約、ユーザーの好み、未解決の疑問、続けるのに必要なデータ |

**Codex（見出しなし）**

見出しは決めず、次の4点を含めるように頼みます。書き方は「簡潔に、構造的に」とだけ指示します。

- 現在の進み具合と、主な決定
- 大事な前提、制約、ユーザーの好み
- 残っている作業（はっきりした次の手順）
- 続けるのに必要なデータ、例、参照

**Cline Desktop（5つ）**

| 見出し | 書く内容 |
|---|---|
| Goal | 何を作っているか、何を直しているかを1文で |
| State | Done（済んだ手順）、In Progress（いまの作業）、Blocked（止まっている原因や未解決の疑問） |
| Highlights | 技術上の主な選択や、目立った発見（なければ省く） |
| Next | すぐ次にやること |
| Files | Read（読んだ）、Edited（編集した）。ハーネスが記録から先に埋めておく |

AIが「Files」を書き落としたときは、ハーネスがあとから足します。

**Pi（6つ）**

| 見出し | 書く内容 |
|---|---|
| Goal | ユーザーが達成したいこと。作業が複数なら複数書く |
| Constraints & Preferences | ユーザーが述べた制約、好み、要件 |
| Progress | Done（済み。チェックつき）、In Progress（作業中）、Blocked（進行を止めている問題） |
| Key Decisions | 決めたことと、短い理由 |
| Next Steps | 次にやること。順番つきの一覧 |
| Critical Context | 続けるのに必要なデータ、例、参照 |

案を切り替えるときの「枝の要約」は、Critical Context を除いた5つです。

**OpenCode（7つ）**

| 見出し | 書く内容 |
|---|---|
| Objective | ユーザーが達成したいことを1〜2文で |
| Requirements | ユーザーが述べた制約、好み、要件、範囲の線引き |
| Decisions | すでに決めたことと、その理由 |
| Work State | 目的を小さな目標に分けて、Completed（済み）、Active（作業中）、Blocked（止まっている原因） |
| Next Move | 次の行動。順番つきの一覧 |
| Relevant Files | 続けるために開く必要があるファイル。最大15件、大事な順、理由つき |
| Important Context | これがないと続けられず、自分では簡単に見つけられない事実 |

### 役割ごとに並べる

| 役割 | DSH | Codex | Cline Desktop | Pi | OpenCode |
|---|---|---|---|---|---|
| 目的 | Primary Request and Intent | － | Goal | Goal | Objective |
| 制約・好み | Critical Context の中 | 頼む | － | Constraints & Preferences | Requirements |
| 進み具合 | Current Work、Pending Jobs | 頼む | State | Progress | Work State |
| 決めたことと理由 | Critical Context の中 | 頼む | Highlights | Key Decisions | Decisions |
| 次にやること | Next Step（1つ） | 頼む | Next | Next Steps（順番つき） | Next Move（順番つき） |
| ファイル | Files and Code | － | Files（記録から） | 見出しなし（記録から末尾に） | Relevant Files（最大15件） |
| エラーと直し方 | Errors and Fixes | － | － | － | － |
| 技術の用語 | Key Technical Concepts | － | － | － | － |
| そのほか大事なこと | Critical Context | 頼む | － | Critical Context | Important Context |

「頼む」は、見出しはないが、含めるように指示しているという意味です。

読み取れること:

- **進み具合の分け方**: Cline Desktop、Pi、OpenCode は「済み／作業中／止まっている」の3つに分けます。DSH は「いまの作業」と「残りの作業」で、「済み」の欄がありません。
- **エラーの欄**: 専用の見出しがあるのは DSH だけです。
- **ファイル**: DSH と OpenCode は AI に書かせます。Cline Desktop と Pi は記録から機械的に作ります。Codex は扱いを決めていません。
- **次にやること**: DSH は1つだけ、Pi と OpenCode は順番つきの一覧です。

### 見出し以外の決まり

| 決まり | DSH | Codex | Cline Desktop | Pi | OpenCode |
|---|---|---|---|---|---|
| 空の見出し | 省かずに「(none)」と書く | － | Highlights は省いてよい | 型どおりに書く。制約と「そのほか」は、なければ「(none)」 | 当てはまらなければ省いてよい |
| 書き方 | 短い箇条書き。段落にしない | 簡潔に、構造的に | 簡潔に、事実だけ | 各見出しを簡潔に | 1行の短い箇条書き。入れ子にしない |
| 正確に残すもの | ファイルの場所、コマンド、エラー文、識別子、数値 | － | － | ファイルの場所、関数名、エラー文 | ファイルの場所、コマンド、エラー文、URL、識別子 |
| ユーザーの言葉 | 言い回しが大事なところは原文。訂正は忠実に残す | － | － | － | まだ答えていない依頼だけ、原文で持ち越す |
| 2回目以降の片付け | 前のメモを写さない。正しいものは残し、古いものは捨てて、1つにまとめ直す | － | 前のメモを一緒に渡す | 前のメモの情報をすべて保つのが基本。不要になったものは消してよい | 前の情報は保つのが基本。ただし新しい履歴を優先し、古くなったものや解決したものは外す |

OpenCode には、ほかにない決まりが3つあります。

- **作業の状態を残す**: 変更が未コミットか、コミット済みか、push 済みか、レビュー中か、マージ済みか。
- **調べ直せることは省いてよい**: コードや、一覧に載せたファイルから次の担当が自分で確かめられることは、書かなくてよい。
- **指示書の内容は書かない**: リポジトリの決まりごとや環境の説明は、次の担当に別に渡るので、メモには含めない。

### メモを頼むときの、会話の見せ方

要約を頼むときに、それまでの会話をAIにどう見せるかも違います。

| ハーネス | 会話の見せ方 |
|---|---|
| DSH | 会話をそのまま並べ直し、最後に指示を足す |
| Codex | 履歴をそのまま使う。入りきらないときは古い側から外す |
| Cline Desktop | 会話をテキストに直して、指示の後ろに付ける |
| Pi | 会話をテキストに直す。作業結果は2,000文字に切り、AIの思考の記録は渡さない |
| OpenCode | ふだんは会話をそのまま送る。大きすぎるときだけテキストに直して縮める |

DSH と OpenCode のソースには、そのまま送る理由が書いてあります。提供元の「キャッシュ」（同じ書き出しの依頼を速く安く処理するしくみ）を使うためです。
Pi のソースには、テキストに直す理由が書いてあります。AIが要約を書かずに、会話の続きを書いてしまうのを防ぐためです。

## 4. 良い点と弱い点（考察）

ここからは、設計を読んだうえでの考察です。同じ会話を5つの型で要約させて比べた結果ではありません。

### 設計の選び方ごとに

| 選び方 | 良い点 | 弱い点 | 当てはまるもの |
|---|---|---|---|
| 見出しが多い | 書き落としが起きにくい。エラーの経緯やコードの一部まで残るので、同じ失敗を繰り返しにくい | メモが長くなり、片付けた直後から机を使う | DSH |
| 見出しが少ない、または自由 | 短い。指示が短いので、型を守りやすい | 制約やエラーの経緯の置き場がなく、落ちやすい。何が残るかはモデルしだい | Cline Desktop、Codex |
| 進み具合を3つに分ける | 済んだ作業が一目でわかり、やり直しを防げる | 済んだ項目がたまっていく | Cline Desktop、Pi、OpenCode |
| 次の一手を1つだけ書く | 直近の依頼から脱線しにくい | 先の計画は、別の欄から読み取る必要がある | DSH |
| 次の手順を一覧で書く | 長い計画を保てる | 古くなった計画に引きずられるおそれがある | Pi、OpenCode |
| ファイルを記録から作る | 抜けや作り話がない | 大事さの順がわからない。長い作業では一覧が長くなる | Cline Desktop、Pi |
| ファイルをAIに書かせる | 「なぜ大事か」がつく。件数を絞れる | 抜けや誤りがありうる | DSH、OpenCode |
| 更新のとき、前のメモを保つことを優先する | 情報が落ちにくい | 片付けのたびにメモが膨らみやすい | Pi |
| 更新のとき、古いものを捨ててまとめ直す | メモの大きさを保てる | まだ必要な情報を、古いと判断して落とすおそれがある | DSH |
| 空の見出しも必ず書く | 形がそろい、何が「なし」かがわかる | 少しだけ長くなる | DSH |
| 会話をそのまま送って頼む | キャッシュが使えて、速く安い | 要約の依頼そのものが机いっぱいの大きさになる。早めに片付ける必要がある | DSH、Codex、OpenCode |
| 会話をテキストに直して頼む | 作業結果を切れるので、依頼を小さくできる | 切った部分は、要約を書くAIにも見えない | Pi、Cline Desktop |

更新の方針では、OpenCode は Pi と DSH の中間です。前の情報を保つのが基本ですが、終わった作業や解決した疑問を外すように、具体的に指示しています。

「更新のたびに膨らむ」ことは、OpenCode で実際に起きていました。ソースのコメントによると、以前の型は、触ったファイルすべてや編集ごとの記録まで残していて、更新のたびに大きくなる欄がありました。いまの型は細かさを抑えてあります。古い型で書かれたメモは、次の更新のときに、いまの細かさで書き直させます。

### 見出しの少なさを補うしくみ

見出しだけを見ると、Codex と Cline Desktop は情報が少なく見えます。実際には、AIを使わない処理が補っています。

- **Codex**: 目的の見出しがありませんが、ユーザーの発言そのものを約2万トークン分残します。目的は、要約ではなく原文で伝わります。
- **Cline Desktop**: ファイルの欄は記録から埋めるので、AIが書き落としても残ります。
- **Pi**: ファイルの見出しはありませんが、記録から作った一覧をメモの末尾に足します。

「AIが書く部分」と「規則で残す部分」を合わせて、1つの引き継ぎになっています。

### ハーネスごとにまとめると

| ハーネス | メモの性格 | 強み | 弱み |
|---|---|---|---|
| **DSH** | 記録重視 | エラーの経緯やコードの一部まで残る。8つの見出しが必ずそろう | メモが長くなりやすい。「済んだこと」の専用の欄がない |
| **Codex** | 自由形式 | 短い。依頼の原文が別に残る | 何がどの形で残るかは、モデルしだい |
| **Cline Desktop** | 最小限 | 短く、守りやすい。ファイルの欄は抜けない | 制約やエラーの経緯の置き場がない |
| **Pi** | 計画重視 | チェックリストとして読みやすい。情報が落ちにくい | 更新のたびに膨らみやすい。ファイルの一覧に大事さの順がない |
| **OpenCode** | 引き継ぎ重視 | 短く保つ決まりが多い。作業の状態（push 済みかどうかなど）を残す | 省いた分は、次の担当が調べ直す必要がある |

### 使い方に合わせるときの目安

ハーネスを選ぶときや、自分で要約の指示を書くときの目安です。

- **エラーを直す作業が多い** → エラーと直し方の欄がある型（DSH）。
- **手順の多い計画を進める** → 進み具合を3つに分け、次の手順を一覧にする型（Pi、OpenCode）。
- **机が小さい、または片付けが何度も起きる** → 書く量を絞る決まりがある型（OpenCode）。
- **ユーザーの細かい指示を守らせたい** → 原文の引用や、依頼の原文を残すしくみがある型（DSH、Codex）。

## 5. 用語の対応

[前の記事の用語の表](compaction.md#7-用語の対応)に足す分です。

| 資料やソースコードでの言葉 | このページでの言い方 | 意味 |
|---|---|---|
| checkpoint、handoff summary | 引き継ぎメモ | 古い会話の要約 |
| template、format | メモの型 | 見出しの並びと、書き方の決まり |
| prune | 中抜き | 長い作業結果の真ん中を落とすこと |
| truncate、clip | 切る | 決まった長さまでで打ち切ること |
| serialize、flatten | テキストに直す | 会話を「[User]: …」のような1本の文章にすること |
| prompt cache | キャッシュ | 同じ書き出しの依頼を、速く安く処理する提供元のしくみ |
| exchange、turn | やり取り | ユーザーの発言1つと、それに続く作業と回答 |
